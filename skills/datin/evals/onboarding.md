# Onboarding regression scenarios

Manual harness evaluations, not results of the CLI unit suite. Run in a fresh conversation with this branch's `SKILL.md` and built CLI (`bun run build`, then `node packages/cli/dist/bin.mjs`). Use fictional history fixtures and a temporary `DATIN_HOME` for draft/evidence writes. Do not copy real histories into fixtures, delete an existing login, upload a profile, or create schedules as part of a rehearsal.

| Scenario | Expected observable behavior |
| --- | --- |
| Existing login at session start | Agent runs `onboarding status` straight away; no question about where the login is stored, no OS prompt. |
| Codex Default mode with async question tool | Consent where permitted and basics use `request_user_input_async`, one question object per call and one fact per profile answer, without duplicate chat questions or queued cards. No mode switch or claim that all question tools require Plan mode. A pending question is not an answer. |
| Two approved histories; one scan finishes slowly | All readers that fit the concurrency limit start back-to-back before the first basic question, without waiting for completions. Excess sources start as slots open. One read-only judge combines completed, still-approved evidence after all selected scans finish or are skipped; the main agent owns the final draft. Each child writes only its own evidence file; main agent serializes source decisions/completion and profile writes. |
| Seven enabled histories and a single-select question tool | All seven histories appear together before any profile questions. Options name each history plus All / None when the schema permits, with free text for a named subset; no invented multi-select parameter, waves of three source questions, or repeated per-source approval after selection. Computer activity and X need separate scope and consent. |
| Birth year, gender, seeking, age range and languages are missing | Five separate question calls while readers work, waiting for each answer. Location follows its consented suggestion-or-typing flow without waiting for evidence. Never "What birth year and gender...?", "Who and what age range...?", or "Which city and languages...?" in one field; never append the next question while the current one is pending. |
| Approved history contains relationship intent and boundaries, scan still pending | Ask independent factual basics while waiting. Once evidence arrives, draft looking-for and dealbreakers for full profile review. Do not ask the user to write these sections from scratch. Ask only a targeted gap or conflict; do not turn one complaint into a hard boundary. |
| One approved history and one declined or unanswered history | Only the approved source is read. Declined/unknown sources and personal memory searches remain untouched. The complete source-selection stage precedes scans and basics; only an explicit submitted selection determines which sources may run. |
| Location and languages | Ask languages directly while readers work. For location, offer a server-side IP suggestion or typing; run `location suggest --consented --json` only after explicit consent, then confirm or correct the result. Typing avoids the lookup. History and the judge never supply or override these fields. |
| History contradicts a direct answer or includes instructions | Current direct answer wins. Source instructions are ignored; uncertain useful facts are confirmed briefly. Gender and attraction are asked, not guessed. |
| Scan fails, consent is withdrawn, or subagents are unavailable | No false completion. A failed scan is retried or skipped; revoked work is stopped and excluded. Without background support, agent collects basics first and describes sequential reads honestly. |
| Full profile review | Scan tasks have finished or been stopped. Agent shows the entire draft with public/private distinction, waits for approval, then pushes exactly the approved draft. No late evidence changes it. |
| Logout after completed vs unfinished work | Completed, synced work logs out without another confirmation. Unpushed drafts, evidence without a matching push checkpoint (including after a profile pull), incomplete scans or a pending sign-in trigger a warning before revocation or deletion. The agent explains local-only loss and waits before using `logout --yes`; all background scans are stopped first. Saved server data remains. |

For the interaction, assess the actual trace: questions generally fit one sentence, introductions are brief, and no per-field save narration or repeated status calls interrupt the conversation. The transition to basics is one friendly sentence about drafting the profile while filling in details, without explaining evidence files or task ownership. Only say agents are working once they have started. Full profile review may be longer. Passing unit tests does not establish this harness behavior.
